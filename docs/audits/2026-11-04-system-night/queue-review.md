# ביקורת תור המדידה

נבדקו תור השימוש והחיבור למדידת חשבונות ב-5.11.2026. הביקורת הפעילה את קוד המקור עם אחסון וזמן נשלטים. לא ניגשה לנתוני ייצור או לחשבון אמיתי.

## הפער ותיקונו

`record` הגביל את מספר האירועים בזיכרון, אך פונקציית הסיום שהחזירה `beginRegistration` הוסיפה תוצאה ישירות ל-`pending`. בניסוי של 800 ניסיונות ותוצאות כאשר `setItem` לא הסתיים, נצברו 1,051 אירועים למרות גבול 500. [המדידה לפני התיקון](queue-review-probe-before.json).

באישור הסוכן הראשי הועברה ההוספה לשגרה המשותפת `append`. היא משמשת כעת גם את התוצאה המאוחרת, שומרת את אותו בעלים וביקור, מאמתת את האירוע ומפעילה את מנגנון פער הכיסוי הקיים. הניסוי החוזר הסתיים ב-500 אירועים. [המדידה אחרי התיקון](queue-review-probe.json), [כלי השחזור](queue-review-probe.cjs).

| ניסוי | תוצאה |
|---|---|
| דחייה קבועה של פעולת מוצר | הוחלפה בפער כיסוי תקין ללא `productKey`, בבעלות החשבון המקורי. |
| בדיוק שבעה ימים ולאחר אלפית שנייה נוספת | הפעולה נשמרה בגבול והוחלפה בפער לאחריו. לא בוצע משלוח בזמן בדיקת התפוגה. |
| 800 פעולות מוצר | לכל היותר 500 שורות שמורות, ובתוכן חיווי פער. |
| שני חשבונות ותור קודם | נשלחה רק פעולת החשבון הפעיל. פעולת החשבון המקורי נשמרה בבעלותו. |
| אוסף חדש מחליף אוסף קודם | עצירת הישן לא כיבתה את החדש. עצירת הנוכחי ביטלה את בעלות המדידה. |
| 800 תוצאות הרשמה בזמן אחסון תקוע | הזיכרון נשאר בגבול 500, ונשמר פער לביקור שנפגע. |
| חזרת האחסון אחרי רצף תוצאות והחלפת חשבון | התור השמור נשאר מוגבל ותקין. התוצאה המאוחרת שמרה את החשבון והביקור המקוריים. מסירת התור לא הכפילה מזהי אירוע. |
